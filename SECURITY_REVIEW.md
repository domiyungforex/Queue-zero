# QueueZero focused security review — 2026-10-02

Scope: authentication, authorization, RLS, tenant isolation, public ticket capabilities, join abuse, rate limits, privileged clients, payments/webhooks, XSS/CSRF, input validation, identifiers, logs, phone privacy and secrets. This is a source review with automated regression checks and read-only production inspection, not a penetration-test certification.

## Concrete findings and fixes

| Issue | Severity | Fix | Remaining risk |
| --- | --- | --- | --- |
| Staff lookup accepted an unverified matching email. A user could attach someone else's unverified address and be selected for that person's staff access. | High | `saveTeamMember` now requires the exact requested email on the selected Clerk account to have `verification.status === 'verified'` before calling the membership RPC. Four negative regression cases reproduced the previous behavior; verified matching addresses still work. | Existing memberships need owner review if previously assigned to unverified addresses. The application cannot retroactively prove historical address ownership. |
| Checkout accepted an unverified primary email despite promising verification. | Medium | Require verified primary email before persisting a checkout or contacting Paystack. Negative and positive regression tests cover this boundary. | Actual Paystack test-mode payment, renewal, cancellation and reconciliation remain unverified in this session. |
| Push registration and payment webhooks checked body length only after buffering the whole request. | Medium | Bounded streaming reader enforces byte limits (8 KiB / 128 KiB), rejects oversized declared bodies early, cancels oversized chunked bodies, and preserves valid UTF-8 signed text. Endpoint tests confirm no privileged work occurs on rejected requests. | Hosting-level request, connection and traffic limits are still needed against distributed or slow-request abuse. |
| New request IDs for the same active ticket created unlimited join-history aliases before the network rate-limit branch. | Medium | Migration `20261002223535_bound_join_retry_records.sql` bounds new records to 60 per customer/queue in ten minutes under the queue lock. Exact replay still works at the limit; other customers are unaffected; history remains intact. Seven SQL regression assertions cover the limit and recovery. | Public joining remains anonymous: rotating cookies across distributed networks can evade identity-based controls. Network rate limiting and the 1,000-active-ticket ceiling remain in force. Apply the new migration before deployment. |
| Administrative RPCs checked manager roles before waiting for locks, so a revoked manager could finish a queued mutation. | High | Migration `20261002223544_recheck_staff_management_authorization.sql` rechecks and locks current membership after resource locks for staff grants, locations, queue creation/settings/status. Overlapping transactions test all five revocation cases. | Apply the migration before releasing these fixes; preserve queue-first lock ordering in future operations. |
| Expired Clerk sessions raised uncaught exceptions in the realtime token endpoint, including provider session details in runtime logs. | Medium | Return generic HTTP 401 with `Cache-Control: no-store` for missing, expired or null tokens. Regression tests cover valid and rejected sessions without logging provider errors. | Earlier deployment logs may retain identifiers until their configured retention expires. Three generic dashboard membership errors in the last 24 hours still need live authentication diagnosis. |
| Nine unrelated tables share the production public schema with RLS disabled and SELECT granted to `anon` and `authenticated`. | Critical deployment blocker | Read-only metadata inspection confirmed `Memory`, `Conversation`, `Permission`, `Agent`, `Wallet`, `Reputation`, `Message`, `SharedContext`, `ApiKey`. No row contents were read. No unrelated application tables were altered. | The shared database owner must remove unintended public grants, implement the other application's policies, or isolate the projects before pilot approval. This cannot safely be solved by guessing another application's access rules. [Supabase advisory](https://supabase.com/docs/guides/database/database-linter?lint=0013_rls_disabled_in_public). |

## Reviewed controls

| Area | Result | Remaining risk / acceptance |
| --- | --- | --- |
| Authentication | Clerk server authentication protects business pages, actions and user database clients. Authorized party is the configured application origin. Database identity uses a Clerk-signed token, never a client-supplied user ID. | Production sign-up HTML and production Clerk script origin are reachable; normal signup, email verification and logout were not exercised with a real test account here. |
| Authorization / tenant isolation | Membership is selected server-side; the business cookie is only a preference. Owner/manager/assigned-staff permissions are independently enforced in SQL. Tenant and role tests pass, including revocation while a queue lock is held. | Provider issuer and JWT-template settings require authenticated provider configuration access. Shared Clerk instances need explicit operational ownership. |
| RLS / privileged functions | All 18 QueueZero production tables have enabled and forced RLS. Anonymous roles cannot read their raw tables. Public functions return narrow projections; protected RPCs authorize the actor and use an empty search path. | Supabase warnings for intentionally public projection RPCs and protected SECURITY DEFINER operations are reviewed, not blanket-disabled. Six internal ledger tables intentionally have no client policies (deny by default). |
| Public tickets / identifiers | Random UUID bearer tokens; public projections exclude customer names, phones, database IDs and customer keys. Invalid tokens return unavailable/404. Display exposes numbers only. Referrer and indexing restrictions protect ticket routes. | Possession of the private ticket URL grants ticket access/cancellation. Do not send those URLs to analytics or support logs. Browser history and device access remain capability exposure risks. |
| Join abuse / rate limits | HMAC browser and network keys; trusted Vercel forwarding header only; fail-closed shared bucket elsewhere; transactional network limit; unique active ticket per browser/queue; idempotent request replay; new alias limit. | Shared business Wi-Fi may reach 60 joins/10 minutes. Confirm expected volume; tune from pilot evidence. Public reads and subscription attempts have no independent per-IP application throttle. |
| Service-role use | Server-only modules; controlled join/cancel/push/outbox/payment paths. Protected business mutations use user-scoped clients and RLS. No server key enters client configuration. | Service-role compromise bypasses RLS, including unrelated shared-project data. Keep deployment/provider access restricted. |
| Webhooks / payment state | Raw-body SHA-512 verification with constant-time comparison; provider transaction lookup matches reference, amount, currency and plan; idempotent transactional event processing. Browser redirect alone cannot activate a plan. | Real provider lifecycle tests and reconciliation are still required. Concurrent/out-of-order provider delivery needs operational monitoring; cancellation must be checked against provider state. |
| XSS / input validation | React escapes business/customer text; Zod validates external input and public API projections; no raw HTML rendering found. Push destinations have an HTTPS provider allowlist; checkout links are restricted to Paystack. | Future HTML/embed features need their own review. No strict script CSP is currently configured. |
| CSRF | Next Server Actions enforce origin checks; push registration requires exact application Origin; webhook authentication is its signature; recovery worker requires a constant-time secret check. | The payment verification GET can be triggered cross-site, but only verifies a stored checkout belonging to the authenticated owner and cannot fabricate payment. |
| Phone privacy | Phone collection is optional and discarded when disabled; public APIs, displays, realtime payloads and the staff console projection omit phone numbers. Raw ticket reads require authorized queue access. | Define retention/deletion and staff access policies before collecting real customer phones. Default phone collection off when unnecessary. |
| Logs / environment secrets | Application log calls contain generic delivery messages rather than raw provider errors, payloads or phone data. `.env*` ignored except examples. Runtime secrets absent from this workspace; production values were not exported. | Provider/access logs may contain bearer URLs. Establish redaction and retention. Historical repository notes mention credentials shared in earlier chat; rotation cannot be confirmed here. |
| Realtime / offline | Private receive-only broadcast policies; invalidation payloads rather than customer records; refetch on reconnect/focus and fallback polling. Worker caches only the generic offline page. | Physical devices and actual Web Push delivery remain acceptance gates. Offline queue state must not be interpreted as current. |

## Evidence and deployment status

- Staff email tests failed on the original code and pass after the fix.
- Lint, strict TypeScript, 353 unit/integration tests, 493 SQL assertions and overlapping-session concurrency tests pass; full browser/build results are recorded in `PRODUCTION_CHECKLIST.md` after final validation.
- `npm audit --omit=dev` reports zero known vulnerabilities in installed production dependencies.
- Read-only hosted inspection confirmed the original 14 migrations and the private Realtime receive policy. The two new security migrations are local and pending deployment.
- The canonical Vercel deployment is READY at original commit `02534e7`, not the new local commits. No production data/configuration was changed during this audit.
- The shared-schema exposure remains a critical blocker. QueueZero must not be called production-ready on this evidence.
